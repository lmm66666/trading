# 设计文档改造：思路、现状与后续交接

更新时间：2026-09-19。本文供下一位 AI 接续工作；记录的是文档改造方案与进度，不是新增业务规则或运行时设计。

## 1. 用户真正要解决的问题

用户原话的核心是：AI 开发变化太快、太多，希望通过开发文档掌控项目；之前用 document-driven-development skill 补齐的文档可读性差，仍像面向 AI 的门禁文档，“自然语言 → 编码语言 → 二进制程序”没有达到预期。

用户明确希望同时支持两种阅读：

- 不看代码，也能理解业务规则、判断系统行为、决定应该怎样改变。
- 需要时能深入数据来源、流转、表关系、接口、索引和关键算法。

用户认可日线 B1 的第一份样稿“好不少”，随后认可整体规划；第一批已完成。不要重新从“是否需要文档”开始讨论，也不要把这项工作退化为换目录、补字段、补审批状态。

**最终验收问题：用户不打开代码，能否解释一个结果为什么产生，指出希望改变的条件，并判断 AI 是否改对？**

## 2. 为什么旧方式没有达到效果

旧文档以源码包和技术契约为组织中心，擅长回答职责、依赖、不可违反的约束，却不擅长回答实际业务问题。

例如，原策略模块解释 Registry、Context、Timeline 和实例隔离，但读者仍要看代码，才能知道 B1 到底何时触发。上一次迁移还明确要求“保持业务内容”，验收主要关注目录、owns 归属、链接、审批和门禁，所以没有真正改善理解业务的路径。

文档管理正确与人能掌控项目是两种验收，前者不能代替后者。也不能只是再增加一套“人话文档”，保留两套完整规则，随后任其各自漂移。

## 3. 改进思路

### 阅读顺序从业务问题开始

按“系统能做什么 → 一件事怎样完成 → 为什么得到这个结果 → 数据与实现怎样支撑 → 怎样验证”组织。

业务流程横跨多个包，应让读者完整读懂一条链路，再按需进入各模块。不要要求用户先理解项目包结构。

### 一条规则有一个完整描述位置

- 扫描流程文档负责扫描窗口、任务、结果含义、数据流和失败场景。
- 日线 B1 文档负责 B1 的参数、公式、判断顺序、候选状态与例子。
- 公共策略模块负责实例隔离、时间线、参数校验、版本和禁止未来数据等技术契约。
- HTTP 契约保留字段全集与精确校验；MySQL 设计保留完整索引、事务与持久化契约。

其他文档只解释与当前场景有关的作用并链接过去，不复制完整规则。少量背景介绍可以重复，但不能有两个独立维护的完整规格。

### 用规则、例子和证据连接自然语言与代码

更合适的闭环是：

```text
业务意图 → 明确规则与实例 → 实现和测试 → 实际行为对照 → 更新当前设计
```

自然语言中的空白会让 AI 自行补齐业务决定。写明判断顺序、边界、失败行为和反例，使这些决定可以被用户看见。

技术细节要解释业务规则如何成立。例如先解释为什么任务固定行情版本，再说明版本保存在哪里、查询如何选修订、哪些约束阻止读到半成品。不要逐函数翻译代码。

### 如实区分现状、意图和证据

- “代码现在这样做”不等于“用户希望这样做”。
- “测试已通过”不等于“文档里的每个例子都有自动化用例”。
- “覆盖率达标”不等于“业务规则已经理解正确”。
- 找不到设计理由时写未知，不给偶然实现编造合理性。
- 发现代码与既有批准设计不一致时，记录双方证据和待决问题，不在文档整理中静默裁决。

## 5. 文档怎样写

不机械要求所有文档填满同一个模板；默认按以下顺序展开：

1. **解决什么问题**：用户提供什么，得到什么，结果应如何理解。
2. **完整走一遍**：用具体输入、处理、输出建立整体认识。
3. **决定结果的规则**：计算口径、公式、判断顺序、状态变化、默认值和边界。
4. **正常、边界与失败例子**：尽量只改变一个条件，让结果差异可以解释。数字应能复算。
5. **数据与技术实现**：来源、转换、保存位置、关联键、索引、事务及接口；字段全集用链接下钻。
6. **验证与未决事项**：测试入口、实际检查范围、静态观察、未知依据和用户需要决定的事。

说明性例子若省略完整历史或指标计算，明确哪些数值是假设输入。不要让读者误以为几根展示的 K 线足以推导所有指标。

正文先给行为、原因和例子；证据、实现链接和元数据放到后面或作为下钻入口。文档长度服务于理解，不以章节齐全为目标。

每次业务变更的第一屏应说明：解决什么问题、相同输入改前改后有什么差异、有哪些选择及取舍、影响哪些数据与历史结果、用什么具体场景验收。完成后回填当前设计，用户不应翻历史变更才能理解现状。

### 当前文档检查有一项刻意保留的边界

`docs/design/workflows/` 和 `docs/design/strategies/` 当前要求：

```yaml
kind: explanation
status: baseline-review
authority: code-derived
baseline_revision: <完整的 40 位代码提交 SHA>
owns: []
```

它们描述现状，不拥有源码、不覆盖批准契约。其他模块／架构／标准仍要求 approved/normative，源码仍恰有一个技术文档所有者。实现位于 `documentation_test.go` 的 `validDesignMetadata`，有正反例测试。

用户认可文档结构，不等于批准全部业务语义。因此不要为了“看起来完成了”把业务说明改成 approved。将来如果要把用户明确确认的业务规则提升为规范，需要设计相应的权威范围与检查方式；当前两目录的检查还不支持这种提升，不应偷偷放宽或强行填批准字段。
