# 策略设计：从日线 B1 扫描读懂系统

这份文档先回答“系统为什么选中这只股票”，再解释“程序和数据库怎样完成这件事”。本次用日线 B1 做完整阅读样例；周线 B1 和底部倍量回撤仍只在后面的公共策略契约中列出，尚未按同样方式展开。

**阅读入口：** [业务规则](#二按什么规则选中一只股票) · [具体例子](#三用一个例子检查我们是否理解一致) · [数据流](#四从行情到结果数据如何流动) · [接口与表](#五接口和表之间怎样关联) · [实现入口](#六想改一条规则去哪里看) · [证据与待判断事项](#七证据限制和需要你判断的地方)。最后的公共策略契约保留所有策略共同遵循的技术约束。

样稿更新：2026-09-19。

## 一、这项能力到底给我什么

你指定证券范围、起始时间和截止时间，系统按日线 B1 的某个固定版本扫描，返回每只证券在这段范围内**最后一根可用日线**上的买入信号。策略标识是 `daily_b1_buy`，当前版本是 `1`。

它寻找的是“先放量上涨，随后有限度回撤，同时均线保持上升、J 值较低”的形态。这句话只是方便理解，准确条件以下文为准。扫描结果是候选名单，不会下单，也不计算收益；同一个策略交给回测引擎时，才涉及持仓、成交和费用。

有两个容易误解的地方：

- 这不是“区间内曾出现过 B1 的全部股票”。即使中途发过信号，最后一根日线不满足，也不会入选本次结果。
- 截止时间是上界，不保证每只证券都有恰好到该时刻的日线。当前实现只要求最后一根日线落在请求范围内，因此要同时看结果的 `signal_time`，不能把所有结果都当成截止当天的信号。

## 二、按什么规则选中一只股票

### 先统一计算口径

涨幅、回撤、20 日均线和 KDJ 都使用前复权价格；成交量使用原始成交量。这里的“日”指数据里的日线根数，不是自然日。指标窗口不足时为无效值，不能把它当成零来参与判断。

以下是默认参数。参数名供你在接口或代码中定位，不影响正文阅读。

| 你可以调整什么 | 默认值 | 准确含义 | 参数名 |
|---|---:|---|---|
| 放量倍数 | 2 | 当日成交量 ÷ 含当日在内的最近 20 根日线均量 ≥ 2 | `volume_ratio` |
| 上涨幅度 | 5% | 当日相对上一根日线的前复权收盘涨幅 ≥ 5% | `rally_pct` |
| 最大回撤 | 15% | 相对跟踪中最高收盘价的跌幅 ≤ 15% | `pullback_pct` |
| 最长回撤 | 10 根 | 当前日线与最近一次达到或超过最高收盘价的日线，索引差 ≤ 10 | `pullback_bars` |
| J 值上限 | 40 | 当日 KDJ 的 J 值必须严格小于 40 | `kdj_threshold` |
| 均线上升检查 | 10 次 | 最近 10 次相邻日线的 MA20 比较都必须严格上升，共涉及 11 个均线值 | `ma_trend_lookback` |

20 日均线和 9 日 KDJ 周期在当前策略中固定，不属于上述可调整参数。KDJ 使用最近 9 根前复权高低价和当前收盘价计算 RSV；K、D 初值均为 50，依次按 2/3 旧值加 1/3 新值平滑，`J = 3K − 2D`。最高价等于最低价时 RSV 取 50。完整计算见 [KDJ 实现](../../../internal/indicator/kdj.go)。

### 每来一根日线，依次做什么

1. **等待放量上涨。** 当天同时满足放量倍数和上涨幅度，开始跟踪，以当天收盘价作为初始峰值。当天不发回撤买入信号。
2. **更新上涨过程。** 后续收盘价达到或超过峰值，就更新峰值及其所在日线。这一天仍不发回撤信号；即使只是与峰值持平，也会重新计算回撤时长的起点。
3. **检查回撤是否有效。** 收盘价低于峰值时，计算回撤深度和时长。超过任一上限，整轮候选失效；否则继续检查买入条件。这里不要求先出现反弹，第一根符合条件的下跌日线就可能入选。
4. **检查均线与 J 值。** MA20 连续严格上升，且 J < 40，才输出买入信号 `daily_b1_pullback`。不满足时不发信号，但不会仅因均线或 J 不合格而清除回撤候选。
5. **遇到新的放量上涨，重新开始。** 新的放量上涨会替换尚未结束的候选，不把两轮上涨拼接起来。这个判断优先于峰值和回撤判断。

**同一轮回撤允许连续多天发信号。** 当前实现没有“发出一次信号便结束本轮”的动作；之后的日线只要仍满足条件，就可能再次发信号。扫描只检查最后一根的决策，回测是否成交则由引擎结合持仓决定。

当收盘价、上一收盘价、成交量或均量不可用，或均量不大于零时，这根日线直接不发信号，也不推进回撤跟踪。均线或 J 不可用则在跟踪推进后阻止当日信号。这些是当前代码行为，不应理解成缺失行情一定会被自动补齐。

## 三、用一个例子检查我们是否理解一致

下面是说明规则的假设输入，省略了此前的指标预热数据。价格均为前复权收盘价；表中明确给出的量比、均线和 J 值视为已计算输入，不声称仅凭这几根价格就能推导它们。

| 日线 | 收盘价与条件 | 系统怎样理解 | 当日买入信号 |
|---|---|---|---|
| D0 | 100 | 尚无候选 | 无 |
| D1 | 106，量比 2.2 | 涨幅 6%，建立放量上涨候选 | 无 |
| D2 | 110，不满足新的放量上涨 | 更新最高收盘价为 110 | 无 |
| D3 | 105，不满足新的放量上涨；MA20 检查通过，J=35 | 从峰值回撤约 4.55%，距峰值 1 根 | 有 |
| D4 | 104，不满足新的放量上涨；MA20 检查通过，J=36 | 回撤约 5.45%，距峰值 2 根；候选仍有效 | 仍然有 |

截止 D4 的扫描返回 D4 的信号，不把 D3、D4 作为两条历史信号都返回。若仅把 D4 的 J 改为 40，则截止 D4 不入选，即使 D3 曾经有信号。

以下边界值得你逐项确认是否符合策略本意。除特别说明外，假设其他必要条件均满足，且当天没有新的放量上涨：

| 边界 | 当前行为 |
|---|---|
| 涨幅恰好 5%，量比恰好 2 | 开始新候选，当天不发回撤信号 |
| 峰值 100，当前收盘 85 | 回撤恰好 15%，深度检查通过 |
| 距峰值恰好 10 根 / 11 根 | 10 根通过时长检查；11 根使候选失效 |
| 当前收盘等于峰值 | 更新峰值日期，不作为回撤 |
| J 恰好为 40，或均线比较中有一次持平 | 不发买入信号 |
| 回撤深度超过 15%，第二天又回到范围内 | 旧候选已失效，不自动恢复，需等待新的放量上涨 |

这些例子是可审阅的行为说明。已有测试覆盖到哪里、哪些边界目前只是静态核对，见第七节。

## 四、从行情到结果，数据如何流动

```text
新浪日线与前复权因子
  → 行情采集：解析、校验后发布完整数据版本
  → MySQL 保存行情及其修订
  → 创建扫描：固定证券集合、数据版本、策略版本和参数
  → Worker 批量加载日线与因子，为每只证券创建独立策略实例
  → 计算指标，按时间顺序回放，再取最后一根日线的决策
  → 原子保存结果快照和任务终态
  → 按同一快照分页读取候选名单
```

扫描计算读取已入库行情，不逐只证券临时请求新浪。创建任务时只选择一次最新的完整行情版本；运行途中有新行情发布，也不切换版本。因此复查结果时要同时保存数据版本、策略版本、参数、时间范围和证券集合。

日线 B1 声明额外加载 30 根预热日线，供指标和顺序回放建立上下文。实现回放包含预热数据，所以起始时间不是“从这里清空策略记忆”的意思；最终返回的信号时间必须落在请求范围内。

扫描范围上限为 5000 个证券，扫描计算 worker 配置为 1–64。它们是现有实现限制，不代表已经测得你的实际使用量。股票与期货行情采集共享限频器；数据来源及采集边界详见 [系统设计](../../architecture/system-design.md)。

如果能确认与前一次快照相比只有部分证券的 Bar 修订，扫描可复用未变化证券的结果；因子或公司行动修订会使整份快照失效并重新计算。缺少变化分类能力时全量计算。具体编排归 [应用层设计](application.md)。

### 失败时，你应该看到什么

- 参数或策略版本非法：创建失败，不静默换成另一组参数或版本。
- 单只证券缺数据或计算失败：记录为失败，其他证券仍可产出结果；失败不是“没有 B1 信号”。
- 取消、租约失效或整体执行失败：不能发布成功快照。
- 后续行情变化：旧快照保持不变；新一次计算可能产生不同结果。

## 五、接口和表之间怎样关联

### 调用顺序

| 你要做的事 | 接口与要点 |
|---|---|
| 创建扫描 | `POST /api/v1/scan-runs`，传 `strategy=daily_b1_buy`、`strategy_version=1`、`from`、`as_of`、`scope` 和 `idempotency_key`；JSON 中版本为字符串 |
| 查询执行状态 | `GET /api/v1/scan-runs/:run_id`，成功或部分成功后取得 `snapshot_id` |
| 读取候选名单 | `GET /api/v1/signal-snapshots/latest`；指定该任务的 `snapshot_id` 定位结果，保留返回的 key |
| 继续读取下一页 | 携带相同快照及其策略、版本、参数 hash，以及服务端返回的 `next_sequence` 作为 `after_sequence` |
| 取消任务 | `POST /api/v1/scan-runs/:run_id/cancel` |

仅按策略查询 latest 可能得到其他参数或其他任务的最新结果，不能用它替代指定任务的结果定位。相同幂等键重试相同请求复用原任务；改变请求内容但继续使用同一键会冲突。完整请求样例和响应字段见 [HTTP 契约](../../standards/http-api.md)。

### 持久化关系

下表是代码模型中的逻辑关联，不表示数据库已经声明了外键。

| 表 | 保存什么 | 怎样关联、为什么这样存 |
|---|---|---|
| `t_instruments` | 证券身份 | 内部证券 ID 被行情和结果行引用，避免只用六位代码造成交易所歧义 |
| `t_market_bars` | 各证券日线及修订 | 按 `instrument_id`、周期、收盘时间定位，按版本有效区间读取任务锁定的历史视图 |
| `t_adjustment_factors` | 复权因子及有效范围 | 以 `instrument_id` 关联证券，并结合生效时间和数据版本选取因子 |
| `t_compute_runs` | 扫描请求、固定输入、执行状态与租约 | `run_id` 唯一；`(kind, idempotency_key)` 唯一约束避免同一请求重复创建任务 |
| `t_signal_snapshots` | 快照头、数据版本和失败分类 | `snapshot_id` 与 `run_id` 各自唯一；当前扫描使用任务 ID 作为快照 ID |
| `t_signal_snapshot_rows` | 入选证券、信号时间和原因 | `snapshot_id` 关联快照头，`instrument_id` 关联证券；未入选且未失败的证券不生成结果行 |

结果行的 `(snapshot_id, instrument_id)` 唯一约束避免一份快照重复收录同一证券；`(snapshot_id, sequence)` 唯一约束为稳定分页提供顺序。行情的 `(instrument_id, timeframe, close_time, revision)` 唯一约束保留不同修订，不能把同一日期的不同版本随意覆盖成一条。

快照头的 `idx_snapshot_latest` 依次包含策略、版本、参数 hash、状态和截止时间，服务相应的快照检索；具体查询计划与性能仍需数据库验证。结果发布由存储层把快照、行、任务终态和完成事件放在同一事务中完成，避免任务显示成功但结果尚未完整写入。完整索引和事务规则归 [MySQL 设计](infrastructure/mysql.md)。

## 六、想改一条规则，去哪里看

| 修改意图 | 主要实现入口 | 同时要考虑什么 |
|---|---|---|
| 调整默认阈值、均线或 J 条件 | [daily_b1.go](../../../internal/strategy/builtin/daily_b1.go)：`dailyParameterSpecs`、`OnBar` | 改默认规则与用户为单次请求传参是两件事；策略行为变化需要新版本 |

| 调整“最后一根”还是“历史全部信号” | [scan_worker.go](../../../internal/application/scan_worker.go)：`replay` | 会影响结果含义、表结构唯一约束和接口，属于业务设计变化 |
| 查看输入固定、批量读取与发布 | [scan_service.go](../../../internal/application/scan_service.go)：`Create`、`Execute` | 证券集合、版本、参数摘要和取消语义必须一起考虑 |

如果你决定“同一轮只发一次信号”，应先明确第一次满足条件以后如何重新获得资格，再更新例子和测试。只加一个布尔开关会掩盖这些业务决定。

| 本文连续信号、均线持平、J=40、等号与陈旧日线等说明 | 对照本文链接的策略、指标和扫描源码 | 本次静态核对；本文的逐行示例没有作为新增自动化测试运行 |

**最值得你先判断的三个问题：** 同一轮回撤是否应连续发信号？均量是否应包含当天？截止日之前较早的最后一根日线是否仍应允许入选？本文说明当前答案，不替你决定它们合理与否。

# 公共策略契约与实现细节

以下内容适用于全部策略。它回答实例如何隔离、如何避免读取未来数据、行为变化如何版本化；日线 B1 的具体业务条件以本文前半部分为阅读入口。

| 属性 | 内容 |
|---|---|
| 状态 | 当前有效 |
| 适用范围 | `internal/strategy`、`internal/strategy/builtin` |
| 最后更新 | 2026-09-14 |

## 1. 职责与非职责

本模块定义编译型策略的静态契约、参数、注册与解析、运行时 Context、跨周期 Timeline 和严格按 Bar 回放的信号决策。`builtin` 提供版本化内置策略。

本模块不读取行情仓储、不决定任务版本、不管理资金、不撮合订单，也不持久化信号。

## 2. 对外能力与使用者

- `Definition` 声明策略 ID、版本、主周期、预热根数、指标依赖、辅助周期、默认持有期和参数规格。
- `Registry` 注册工厂、列出稳定定义，并按 ID/版本/参数创建全新策略实例。
- `Timeline` 组合主周期 Dataset、指标集合和只向历史对齐的辅助周期。
- `Context` 只暴露当前 Bar、当前位置和当前或历史特征值。
- `ReplayLatest` 顺序回放一个实例并返回最后决策。

扫描服务、回测引擎、策略目录 API 和图表/计算编排使用这些能力。

## 3. 依赖和边界

只依赖 `internal/market`、`internal/indicator` 和 Go 标准库。策略实例不能获得 Repository、HTTP 客户端、系统时钟或完整未来切片。

应用层负责锁定 Definition、参数、数据与引擎版本；策略模块负责验证这些输入彼此兼容。

## 4. 核心模型与不变量

### 4.1 定义与版本

- ID、Version、主周期必填；预热和默认持有期不得为负。
- 指标引用必须合法、键不重复，且周期属于主周期或已声明辅助周期。
- 参数名非空，默认值和用户值必须有限、位于闭区间；整数参数不得接受小数。
- 同一策略行为改变必须新增策略版本。版本 1 当前包含 `daily_b1_buy`、`weekly_b1_buy`、`bottom_surge_pullback`。

### 4.2 Registry 与实例隔离

- `(ID, Version)` 在 Registry 内唯一，未知或重复注册失败。
- Registry 防御性复制定义、参数规格和传入参数。
- 每次 Resolve 调用工厂并返回独立实例；扫描不同证券不得共享可变策略状态。
- 工厂返回 nil、改变静态定义或产生非法定义时解析失败。

### 4.3 时间线与 Context

- 主/辅助 Dataset 必须合法，并属于相同证券和数据版本。
- 辅助索引必须是主 Bar 截止时最新且已收盘的 Bar，不能映射未来值或更旧替代值。
- `Float(ref, ago)` 只能读取当前索引及历史，负 ago、越界或无效指标会设置 Context 错误或返回无效。
- Timeline 防御性复制特征映射和对齐关系，调用者不能在回放中篡改输入。

### 4.4 决策

策略动作仅为 Hold、EnterLong、ExitLong。策略必须先检查指标有效位，再作判断。扫描回放中的 PositionView 为空；回测 Context 由引擎提供真实持仓视图。

## 5. 主要流程

```text
Registry 固定定义
  → 校验并补齐参数
  → 创建单次、单证券策略实例
  → 构造 Timeline 和特征集合
  → 从最早 Bar 顺序调用 OnBar
  → 返回决策或交给回测引擎排单
```

内置策略的金样本和前缀测试定义当前版本行为；不能在相同版本下静默改变判断条件、预热、参数默认值或跨周期对齐方式。

## 6. 失败、取消和一致性语义

- Definition、参数、Timeline 或特征不兼容时，在调用策略逻辑前失败。
- OnBar 返回错误或尝试未来/越界访问时，Replay 立即失败，不返回看似有效的最后信号。
- Replay 不自行处理 context；长批量任务在应用层和回测 Bar 边界实施取消。

## 7. 性能与安全约束

- 单次 Replay 对 Bar 顺序遍历，策略内部不得访问外部系统或执行无界工作。
- 指标在进入策略前统一构建，策略不为每根 Bar 重算完整历史。
- 参数与定义复制避免调用者共享可变 map/slice 引起跨任务污染。

## 8. 测试与验收证据

测试覆盖非法定义全集、Registry 实例隔离、参数边界、Timeline 防御性复制、未来数据拒绝、辅助周期 as-of 对齐、内置策略金样本和前缀不变性。

