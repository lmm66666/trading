# REQ-2026-001：以设计文档为核心的文档治理

| 属性 | 内容 |
|---|---|
| 状态 | 已完成 |
| 创建日期 | 2026-09-14 |
| 适用范围 | 整个仓库 |
| 目标版本 | 文档治理第一版 |

## 1. 背景

当前根目录 `AGENTS.md` 同时承载项目概述、开发约束、架构设计、运行说明和具体业务规则；部分模块的 `README.md` 又同时记录模块设计、实现细节和验证命令。这样的组织存在以下问题：

1. 全局规则与模块知识混在一起，任何任务都会加载大量无关上下文。
2. 同一条设计约束可能同时出现在根文档、模块文档和 API 文档中，缺少明确的权威来源。
3. 需求完成后，代码保留了结果，但“为什么这样设计”和“影响了哪些模块”难以追溯。
4. 代码评审缺少稳定的设计基线，容易退化为只检查局部实现。
5. 模块文档偏实现说明，没有统一回答职责、边界、不变量、失败语义和验证方式。

本需求建立一套以设计文档为核心的文档体系。设计文档定义系统应当如何工作，测试证明实现符合设计，代码是设计的可执行实现。

## 2. 目标

1. 明确不同层级文档的职责和权威边界。
2. 让每个长期存在的模块维护一份当前有效的 `DESIGN.md`。
3. 为大型需求建立从提出、评审、实现到归档的完整记录。
4. 让轻量缺陷修复直接修订对应模块设计，无须创建独立需求文档。
5. 让文档评审先于代码评审，并成为合并门禁的一部分。
6. 降低 Agent 和开发者理解模块时需要加载的上下文范围。

## 3. 非目标

1. 不为每次格式调整、拼写修正或依赖补丁创建需求文档。
2. 不建立独立 ADR 目录。跨模块决策的方案比较和理由先保存在需求文档中；确有长期独立价值时再引入 ADR。
3. 不把设计文档写成源代码逐行说明、提交日志或缺陷流水账。
4. 不复制可由代码、生成工具或测试报告可靠得出的低层信息。
5. 本次不引入文档网站、专用生成器或外部知识库。

## 4. 核心原则

### 4.1 设计先于实现

- 大型需求先形成并批准需求文档，再修改目标设计，最后开始实现。
- 轻量缺陷先补充或澄清模块设计中的规则、边界或失败语义，再编写失败测试和修复代码。
- 开发过程中发现设计遗漏时，先修订文档并完成相应评审，再继续偏离原设计的实现。

### 4.2 文档描述意图，代码实现意图

- `DESIGN.md` 描述模块当前或本开发分支目标状态下的行为，不描述文件逐行实现。
- 测试把关键设计规则转成可执行证据。
- 代码与设计冲突时必须暂停受影响的实现，向用户列出具体差异、可选处理及影响，由用户明确决定以设计修正代码，或先修订设计再继续实现。Agent 不得自行选择权威一方。

### 4.3 当前事实与变更历史分离

- 模块 `DESIGN.md` 是当前设计事实，读者无需查阅历史需求即可理解模块。
- 需求文档记录一次变更的背景、范围、方案、取舍和验收结果。
- 需求完成后归档，但其中已经生效的规则必须合并回对应 `DESIGN.md`，不能只留在历史需求中。

### 4.4 单一权威来源

同一规则只在最合适的层级完整定义，其他文档通过相对链接引用，不复制正文：

- 全仓开发流程由 `AGENTS.md` 定义。
- 跨模块边界由 `docs/architecture/` 定义。
- 模块内部行为由模块 `DESIGN.md` 定义。
- 外部 HTTP 契约由 `api/api.md` 定义。
- 一次变更的动机与验收由对应需求文档定义。

### 4.5 冲突必须显式消解

代码与文档、文档与文档之间出现冲突时不得按“优先级”猜测正确答案：

1. 暂停受冲突影响的实现和合并。
2. 向用户说明冲突位置、当前代码行为、文档规定、可选处理和各自影响。
3. 等待用户明确决定正确语义；未经决定不修改任意一方来消除冲突。
4. 用户决定改变设计时，先修订并评审所有受影响的权威文档；决定保持设计时再修正代码。
5. 补充能够证明最终语义的测试。

`AGENTS.md` 约束开发过程，不覆盖产品或模块设计；需求文档描述变更，不允许长期替代模块设计。

## 5. 文档结构

```text
trading/
├── AGENTS.md
├── docs/
│   ├── roadmap.md
│   ├── operations.md
│   ├── architecture/
│   │   ├── system-design.md
│   │   └── domain-map.md
│   ├── requirements/
│   │   ├── active/
│   │   └── archived/
│   └── templates/
│       ├── module-design.md
│       └── requirement.md
├── api/
│   ├── DESIGN.md
│   └── api.md
└── <module>/
    └── DESIGN.md
```

### 5.1 `AGENTS.md`：开发宪法

只保留对全仓所有任务长期生效的内容：

- 项目一句话定位与核心业务边界。
- 文档权威关系和文档 SOP。
- 全局架构依赖方向。
- 通用代码、日志、数据库、测试、Git 和安全规范。
- 当前 roadmap 阶段的简短摘要及 `docs/roadmap.md` 链接。
- 架构文档、模块设计和 API 契约的索引。

不得放入：

- 单个模块的完整实现设计。
- 单个接口的请求响应示例。
- 一次需求的实施细节。
- 会频繁变化的完整 roadmap。

### 5.2 `docs/roadmap.md`：演进方向

记录产品与技术路线，而不是任务清单：

- 当前阶段目标和成功标准。
- 已完成、进行中、候选三个层级。
- 关键依赖和明确的重新评估条件。
- 每个大型事项链接到对应需求文档；不复制需求正文。

roadmap 允许调整方向，但不能替代已批准的需求和模块设计。

### 5.3 `docs/operations.md`：运行手册

集中记录本地启动、配置、Docker、数据库维护窗口、迁移入口和常见运行限制。运行手册描述如何安全操作当前系统，不承担模块设计或开发流程规范。

### 5.4 `docs/architecture/system-design.md`：系统级设计

记录跨模块长期有效的整体结构：

- 系统上下文和主要运行进程。
- 分层、依赖方向和组合根。
- 关键端到端数据流。
- 版本、一致性、时间和身份等全局语义。
- 外部系统边界和主要质量属性。

具体模块算法、字段清单和 API 示例应留在模块设计或接口文档中。

### 5.5 `docs/architecture/domain-map.md`：领域与模块地图

以表格维护每个模块的职责、公开边界、依赖关系、设计文档路径和维护状态。它只负责导航和边界检查，不复制模块设计。

### 5.6 模块 `DESIGN.md`：当前设计事实

长期存在且具有独立职责的模块必须维护 `DESIGN.md`。第一版覆盖：

- `api`
- `business`
- `data`
- `internal/market`
- `internal/indicator`
- `internal/strategy`
- `internal/backtest`
- `internal/application`
- `internal/financialscreen`
- `internal/port`
- `internal/infrastructure/mysql`
- `pkg/broker`
- `web`
- `cmd/migrate-strategy-kernel`

纯粹的文件分组、小型工具目录和没有独立业务语义的目录无需为了形式单独创建文档，其约束归入最近的上级模块。

每份模块设计使用统一章节：

1. 职责与非职责
2. 对外能力与使用者
3. 依赖和边界
4. 核心模型与不变量
5. 主要流程
6. 失败、取消和一致性语义
7. 性能与安全约束
8. 测试与验收证据
9. 相关文档

章节可以省略确实不适用的内容，但不得保留空章节或占位文字。

### 5.7 `docs/requirements/`：大型变更记录

大型需求文件命名为 `REQ-YYYY-NNN-<topic>.md`。编号在仓库中唯一，`topic` 使用小写连字符英文名称。

需求状态固定为：

```text
待评审 → 已批准 → 开发中 → 待合并 → 已完成
              ↘ 已取消
```

- `active/` 保存“待评审”至“待合并”的需求。
- `archived/` 保存“已完成”或“已取消”的需求。
- 状态变化必须修改文档元数据，不能仅体现在任务系统或提交信息中。

需求文档至少包含：

1. 背景与问题
2. 目标和非目标
3. 当前行为
4. 目标行为
5. 受影响模块及文档
6. 方案比较和选择理由
7. 数据、接口和兼容性影响
8. 风险与失败处理
9. 测试和验收标准
10. 实施过程中形成的设计修订
11. 最终验收结果
12. 开发中发现的代码—设计冲突及用户裁决

### 5.8 `api/api.md`：外部接口契约

保留现有接口文档作为 HTTP 契约的权威来源。`api/DESIGN.md` 只描述传输层职责、校验策略、错误映射、依赖边界和兼容策略，不复制每个接口的完整请求响应。

## 6. 变更分类

### 6.1 大型需求

满足任一条件即按大型需求处理：

- 新增业务能力、模块或端到端流程。
- 改变公开 API、持久化语义、策略语义或引擎语义。
- 涉及两个及以上模块的职责或接口调整。
- 包含数据库迁移、历史数据重写或兼容方案。
- 引入新的基础设施、外部依赖或并发模型。
- 风险较高，无法用一个局部回归测试充分描述。

大型需求必须创建需求文档，并更新所有受影响模块设计。

### 6.2 轻量缺陷

同时满足以下条件才可按轻量缺陷处理：

- 不新增产品能力。
- 不改变公开契约或已批准业务语义。
- 修改范围局限在单个模块内。
- 不需要数据迁移或跨版本兼容。
- 可以用明确的回归测试证明修复。

轻量缺陷不创建独立需求文档，但必须对对应 `DESIGN.md` 产生有意义的修订：补充缺失的不变量、边界条件、失败语义或验证证据。设计文档不得追加按日期排列的缺陷流水账。

一旦实现过程中发现跨模块影响或语义变化，应立即升级为大型需求，创建需求文档后再继续。

### 6.3 机械性维护

纯格式化、拼写修正、等价重构或不改变行为的依赖补丁不强制修改设计正文。变更说明必须声明“无设计语义变化”，评审者需核实该判断。若无法明确证明等价，则升级为轻量缺陷或大型需求。

## 7. SOP

### 7.1 大型需求流程

#### 阶段一：需求设计

1. 从模板创建 `docs/requirements/active/REQ-*.md`，状态为“待评审”。
2. 描述问题、目标、非目标、候选方案和验收标准。
3. 列出所有受影响的架构、模块和接口文档。
4. 完成需求评审；批准后状态改为“已批准”。

在批准之前，不编写生产实现代码。只允许进行明确标记为一次性的可行性验证。

#### 阶段二：目标设计

1. 在开发分支中先修改受影响的架构文档和模块 `DESIGN.md`，使其描述合并后的目标状态。
2. 修改接口时同步更新 `api/api.md`。
3. 检查不同文档之间的职责、术语和语义是否一致。
4. 完成设计评审后，把需求状态改为“开发中”。

主分支文档始终描述当前生产设计；开发分支文档可以描述该分支准备交付的目标设计。

#### 阶段三：测试与实现

1. 根据验收标准和设计不变量编写失败测试。
2. 实现满足设计所需的最小代码。
3. 新发现的边界或取舍先写回需求和模块设计，再实现。
4. 不得以“代码已经写完”为理由跳过或弱化设计变更。

#### 阶段四：交付评审

评审按固定顺序进行：

1. 需求评审：目标和验收标准是否完整实现。
2. 设计评审：模块文档是否准确描述最终系统，文档之间是否一致。
3. 测试评审：关键规则是否有可执行证据，覆盖率是否达标。
4. 代码评审：实现是否正确、简单并符合设计。

任一上游评审未通过，不进入下一层评审。

#### 阶段五：完成与归档

1. 在需求文档记录最终验收命令、结果和必要的设计偏差说明。
2. 确认所有已生效规则均已进入架构或模块设计文档。
3. 将需求状态改为“已完成”，移入 `docs/requirements/archived/`。
4. 合并开发分支。
5. 切回 `main` 并清理已合并分支。

### 7.2 轻量缺陷流程

1. 确认变更符合轻量缺陷的全部条件。
2. 找到缺陷对应的模块 `DESIGN.md`。
3. 先补充或澄清被缺陷暴露的设计规则。
4. 编写能够复现缺陷的失败测试。
5. 修复代码并运行模块级和全量验证。
6. 评审设计修改、测试证据和代码是否表达同一规则。

如果找不到归属模块，说明领域边界或文档地图存在缺口，应先修订 `domain-map.md`，必要时升级为大型需求。

### 7.3 文档自身的变更流程

- 只澄清措辞且不改变语义时，按机械性维护处理。
- 改变模块职责、业务规则或外部契约时，按对应的软件变更级别处理。
- 改变本文档定义的治理流程属于大型需求，必须通过新的需求文档修订。

## 8. 评审规范

### 8.1 需求文档评审清单

- 问题是否真实存在，并有清晰边界。
- 目标是否可验证，非目标是否排除无关扩张。
- 方案是否包含必要的取舍，而不是只有结论。
- 是否列全受影响模块、接口、数据和兼容性。
- 是否定义失败、取消、回滚或恢复语义。
- 验收标准能否直接转化为测试或可重复验证命令。

### 8.2 模块设计评审清单

- 新成员能否不读实现就理解模块职责和边界。
- 每条重要规则是否只有一个权威定义位置。
- 公开能力、核心不变量和失败语义是否明确。
- 是否描述“为什么”和“必须满足什么”，而非逐文件复述代码。
- 是否存在过期内容、复制内容、空章节或未解释缩写。
- 测试证据是否能对应关键设计规则。

### 8.3 代码评审入口条件

代码评审开始前必须满足：

- 变更已正确分类。
- 大型需求已经批准，且需求状态至少为“开发中”。
- 所有受影响的设计和接口文档已更新。
- 新增或修改的设计规则已有测试证据。
- 快速检查全部通过；交付前完整验证满足项目门禁。

## 9. 提交与合并规范

文档和实现按意图拆分提交：

1. `docs: define <topic> design`
2. `test: cover <behavior>`
3. `feat:`、`fix:` 或 `refactor:` 实现提交
4. `docs: finalize <requirement>`

小型变更可以减少提交数量，但一个提交仍只表达一件事。大型需求的首个可评审提交应只包含需求与目标设计，不与生产实现混合。

合并说明必须回答：

- 这是大型需求、轻量缺陷还是机械性维护。
- 哪份文档定义本次变更。
- 哪些测试证明代码符合设计。
- 是否存在没有解决的设计偏差；存在则禁止合并。

## 10. 第一版迁移方案

### 10.1 根文档

精简 `AGENTS.md`，保留开发宪法、全局不变量、SOP 和文档索引。把具体架构、运行流程和模块规则迁移到其权威位置。

### 10.2 系统文档

创建：

- `docs/roadmap.md`
- `docs/architecture/system-design.md`
- `docs/architecture/domain-map.md`
- `docs/templates/module-design.md`
- `docs/templates/requirement.md`

### 10.3 模块文档

- 将现有 `api/README.md` 重构为 `api/DESIGN.md`，保留 `api/api.md` 作为接口契约。
- 将 `internal/application/README.md` 重构为模块设计。
- 将 `internal/infrastructure/mysql/README.md` 重构为模块设计。
- 将 `model/README.md` 的有效约束并入所属模块设计或 `AGENTS.md`，避免继续维护缺少独立业务职责的根级模型说明。
- 根据源码和测试为第 5.6 节列出的其余核心模块补齐 `DESIGN.md`。

迁移时必须验证内容归属，不能只进行机械改名。重复规则保留一个权威定义，其余位置改为链接。

## 11. 验收标准

1. `AGENTS.md` 不再承载单个模块的详细设计和完整 API 示例。
2. roadmap、系统设计、领域地图和两份模板全部存在，互相链接有效。
3. 第 5.6 节列出的核心模块都有符合模板的 `DESIGN.md`，或在领域地图中明确说明为何归属于上级模块。
4. 现有文档内容完成迁移，没有因改名或拆分丢失有效约束。
5. 同一关键规则不存在互相冲突的重复定义。
6. 大型需求、轻量缺陷和机械性维护均有明确、可执行的 SOP。
7. 文档评审、测试评审和代码评审的先后关系已写入全局规范。
8. 仓库内部 Markdown 相对链接检查通过。

## 12. 风险与控制

### 12.1 文档膨胀

控制方式：模块文档只记录长期设计，不记录代码清单和变更流水；历史原因留在需求文档。

### 12.2 文档与代码漂移

控制方式：先评审文档，再评审测试和代码；大型需求在验收时逐项核对受影响文档。

### 12.3 规则重复

控制方式：领域地图标识权威文档；其他层级只保留摘要和链接。

### 12.4 形式主义

控制方式：轻量缺陷不创建需求文档，机械性维护不强制制造无意义的设计差异；文档深度按风险和影响范围调整。

### 12.5 迁移遗漏

控制方式：先建立文档地图，再逐条迁移现有 `AGENTS.md` 和 `README.md` 内容；删除旧内容前确认新权威位置和链接。

## 13. 开发中设计修订

实施根文档迁移时确认，本地启动、Docker 和停机维护命令属于长期运行知识，但不属于 `AGENTS.md` 的开发宪法，也不应塞入系统架构设计。第一版增加 `docs/operations.md` 作为运行手册；该文件不改变产品或模块语义，只承接现有有效操作说明。

用户进一步明确：设计文档虽是实现基线，但 Agent 发现代码与设计不一致时没有自行裁决权。SOP 增加“暂停、说明差异和影响、询问用户、按裁决先更新设计或修正代码”的强制门禁。

## 14. 代码—设计冲突与用户裁决

完整验证中暴露的 Broker 限频测试不稳定属于测试断言与实现计时边界不一致，不是已有设计文档与代码行为冲突。用户明确同意把它作为轻量缺陷处理；修复前先更新 `pkg/broker/DESIGN.md`，生产代码未修改，测试改为在受控 `RoundTripper` 入口观测请求放行时间。

- 领域地图如实列出当前直接依赖，并把旧业务链路标记为不得扩大的兼容边界。

- 新行情适配器与旧 `SinaBroker` 的限频、重试和响应上限分别定义；旧行为不作为新代码范式。

未来统一兼容边界属于大型需求候选，记录在 Roadmap；本需求不改变生产行为。
