## 长期愿景

建设一个面向 A 股和大宗商品期货的行情、财报、指标、策略扫描与回测平台。策略以版本化 Go 实现为当前基础，长期逐步获得类似 TradingView 的指标组合、策略表达、可复现回测和交互分析能力。

Roadmap 表达方向和进入条件，不等同于已批准需求。大型事项只有进入需求文档的“已批准”状态后才能开始生产实现。

## 当前阶段：策略内核与行情工作台稳定化

当前阶段的成功标准：

- 行情、指标、策略、扫描和回测遵守统一时间线，不读取未来数据。
- 任一计算能够固定行情版本、策略版本、参数和引擎版本后重复执行。
- 全市场扫描在 5000 个证券规模下使用有界批量读取和固定 Worker。
- API 与行情工作台在固定快照或固定行情版本上稳定分页。
- MySQL 5.7 与 8.0 的持久化、租约、并发和迁移语义有真实集成测试。
- 需求、设计、测试和代码建立可审查的追踪关系。

### 已完成的基础能力

- 版本化股票与期货主力连续行情，日线和本地确定性周线。
- SMA、EMA、MACD、KDJ 指标图与有效位传播。
- 版本化内置策略、严格时间线 Replay、回测账户与撮合。
- 持久化回测/扫描任务、租约、取消、重试、不可变快照和游标分页。
- React 行情工作台、证券搜索、固定版本 K 线分页与指标交互。
- 旧行情到新内核的可检查点、可重跑迁移命令。

### 当前重点

1. 完成文档治理自举，使模块设计成为代码实现的上游约束，见 [REQ-2026-001](requirements/active/REQ-2026-001-document-governance.md)。
2. 持续校准数据完整性、策略语义和端到端可复现性。
3. 用真实运行指标验证 MySQL 队列、批量扫描和行情发布的容量边界。
4. 在不牺牲固定版本语义的前提下完善工作台分析体验。

## 候选方向与进入条件

### 更丰富的指标和策略表达

只有现有指标图、策略版本和回测时间线保持稳定后，才评估组合指标、用户参数化策略或脚本能力。任何新表达能力都必须保留确定性、版本化和禁止未来数据的约束。

### Redis Streams 任务队列

第一阶段保持 MySQL-only。只有出现以下任一持续指标才创建迁移需求：

- MySQL 队列领取或续租 P95 持续超过 100ms。
- 待执行任务积压持续超过一个扫描周期。

即使迁移队列，MySQL 仍保存最终结果和审计记录；需求必须重新定义事务边界、幂等、租约和故障恢复。

### Kafka 行情事件日志

只有行情需要多个独立消费者、跨服务重放，或峰值吞吐达到单库发布瓶颈时才创建引入 Kafka 的需求。数据库版本发布仍需保持原子性。不得仅因为逐证券查询性能问题引入消息系统；该问题应首先由正确的批量查询模型和索引解决。

### 可交割合约与连续合约研究

当前期货只保存上游定义的 `.MAIN` 主力连续序列。保存具体合约、自行换月或连续序列复权属于新的数据产品，必须先验证来源稳定性、字段语义、换月规则和历史完整性，并以独立需求推进。

### 兼容边界收敛

当前财报、宏观和旧 HTTP 能力仍通过 `api -> business -> data/model/pkg` 兼容链路运行；旧 `SinaBroker` 的限频、重试、错误分类和响应上限也与新行情适配器不同。只有准备改变或下线兼容接口，或运行指标证明现有边界产生稳定性、安全或维护瓶颈时，才建立大型需求统一这些行为。

需求必须分别定义 API 兼容策略、数据迁移、外部来源失败语义和依赖方向；不得在普通缺陷修复中顺带移动模块或改变公开行为。

## Roadmap 维护规则

- “已完成”必须由已归档需求、测试或已合并实现支持。
- “当前重点”最多保留少量阶段目标，不用作个人任务列表。
- “候选方向”必须包含进入条件，避免把想法误读为承诺。
- 方向变化更新本文件；具体业务行为更新需求和模块设计。
- 完整系统边界见 [系统设计](architecture/system-design.md)，模块归属见 [领域地图](architecture/domain-map.md)。
