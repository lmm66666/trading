## 1. 背景与问题

开发机和部署环境使用不同 CPU 架构：本地 Docker 宿主为 `linux/arm64`，部署环境为 `linux/amd64`。现有集成测试依次启动 `mysql:5.7` 和 `mysql:8.0`；MySQL 5.7 官方镜像在本地缺少原生 ARM64 支持，会触发跨架构模拟，增加耗时和失败面。

部署数据库的只读协议握手显示版本为 MySQL 8.4.5。项目继续承诺 MySQL 5.7/8.0 双版本会让设计、测试矩阵和实际部署基线长期分离。

## 2. 目标

1. 将项目唯一受支持的数据库基线统一为 MySQL 8.4 LTS。
2. 本地 ARM64 环境不启动、不拉取 MySQL，也不承担 MySQL 验收。
3. 所有真实 MySQL 集成测试连接获批的远端 AMD64 MySQL 8.4，为每个测试创建随机隔离数据库并在结束时删除。
4. 部署应用镜像明确构建为 `linux/amd64`，与生产宿主一致。
5. 删除文档、测试和代码注释中的 MySQL 5.7/8.0 双版本承诺。

## 3. 非目标

- 不修改业务表结构、持久化语义或已有数据。
- 不因升级基线而改用 `SKIP LOCKED`、窗口函数等 MySQL 8 专属实现。
- 不在任何现有业务数据库中运行 AutoMigrate、集成测试或写入语句。
- 不把部署密码、完整 DSN、内网地址或端口写入 Git 跟踪文件。
- 不建设多架构发布流水线或镜像仓库推送流程。

## 4. 当前行为

- 11 个集成测试文件的 17 个位置分别硬编码 `[]string{"mysql:5.7", "mysql:8.0"}`。
- `scripts/verify.sh` 宣称并执行 MySQL 5.7/8.0 双版本门禁，最终应用镜像只按当前 Docker 宿主构建。
- `AGENTS.md`、系统设计、运行手册、Roadmap 和 MySQL 模块设计继续承诺两个旧版本。
- 本地宿主和 Docker daemon 均为 ARM64；部署数据库协议版本为 MySQL 8.4.5。

## 5. 目标行为

### 5.1 数据库版本

获批的远端 MySQL 8.4 服务是唯一集成测试目标。测试夹具读取仓库根目录下、本地保存且不纳入 Git 的 `config.yaml` 数据库配置，为每个测试生成仅含受控字符的随机数据库名，创建空数据库、运行现有测试，并通过 `t.Cleanup` 删除该数据库。

DSN 的基准数据库名不会作为测试目标；测试连接必须改写到新建的随机数据库，从结构上避免误用现有业务库。测试进程异常终止可能留下带 `trading_test_` 前缀的孤立数据库，只能在人工确认创建时间和无活跃测试后清理。

最低运行版本为 MySQL 8.4。现有 SQL 可以继续采用兼容写法；删除 MySQL 5.7 支持不授权顺带重构队列、迁移或锁实现。

### 5.2 架构矩阵

| 环境 | CPU 架构 | 验证方式 |
|---|---|---|
| 本地开发 | `linux/arm64` | 运行单元、前端、Race 和静态检查，不运行本地 MySQL |
| 远端集成数据库 | `linux/amd64` | 先只读验证版本/架构，再使用随机隔离数据库运行真实集成测试 |
| 部署应用镜像 | `linux/amd64` | Buildx 显式按 `linux/amd64` 构建 |

完整门禁必须读取本地 `config.yaml`；缺少文件、配置无效、连接失败或无法创建随机隔离数据库时失败，不回退到环境变量、本地容器、SQL mock 或只编译。

### 5.3 部署检查

部署预检只允许从本地 `config.yaml` 建立连接、`PingContext`、查询 `VERSION()` 与 `@@version_compile_machine`。确认 MySQL 8.4.x 和 x86_64 后，集成夹具才可创建随机隔离数据库。错误消息不得打印配置路径、DSN、地址、用户名或密码。

完整集成测试可以在隔离数据库中执行 DDL、DML、事务和锁测试，但不得枚举、读取或修改其他数据库。测试结束时删除自己的随机数据库。

## 7. 方案比较与选择

选择远端 MySQL 8.4 LTS 验收，而不是继续双版本、本地容器或固定 8.0：

- 8.4 与当前部署数据库 8.4.5 一致，减少环境漂移。
- 测试直接覆盖实际部署版本和 CPU 架构，避免 ARM64 本地模拟 amd64。
- 每个测试使用随机隔离数据库，在共享服务上保持结构与数据隔离。

未选择本地 MySQL 镜像或 amd64 模拟，因为用户明确要求只在部署数据库验收；也不在现有业务库直接运行测试。

## 8. 接口、数据与兼容性

HTTP API、领域模型和表结构不变。部署数据库已经是 MySQL 8.4.5，因此无需业务数据迁移。

本变更明确终止 MySQL 5.7 和 8.0 的支持承诺；仍运行这些版本的环境必须先自行升级到 8.4，项目不提供双版本兼容期。

## 9. 风险与失败处理

- 本地配置缺失或无效、连接失败、版本不是 8.4.x 或架构不是 x86_64 时明确失败，但只输出脱敏分类。
- 创建数据库失败时不得尝试使用 `config.yaml` 中的业务数据库继续测试。
- 创建数据库响应丢失或超时时结果可能不确定，因此必须在执行 CREATE 前注册幂等清理，并在失败退出时执行 `DROP DATABASE IF EXISTS`。
- 清理失败必须使测试失败并报告随机数据库名，便于人工恢复；数据库名不包含凭据或业务标识。
- 预检绝不调用 `Migrate`、AutoMigrate 或业务 Repository；写入测试仅在新建随机数据库内执行。

## 10. 测试与验收标准

1. 仓库正式文件中不存在 MySQL 5.7/8.0 双版本支持声明或 `mysql:5.7` 测试镜像。
2. 文档契约测试、快速检查和 `bash scripts/verify.sh` 全部通过。
3. 本地验证不启动或拉取 MySQL 镜像；真实集成测试只连接远端随机隔离数据库。
4. 部署预检报告 MySQL 8.4.x 和 x86_64，不输出连接凭据；全部集成测试通过且隔离数据库清理完成。
5. 最终应用镜像以 `linux/amd64` 成功构建。
6. 总覆盖率和核心领域覆盖率继续满足 `AGENTS.md` 门禁。

## 11. 开发中设计修订

完整门禁的旧版本行为已被实际复现：ARM64 本地运行启动了 `mysql:5.7`，随后在拉取 `mysql:8.0` 时遇到 Docker Registry 超时。第一次批准的方案准备改用本地原生 `mysql:8.4`，但用户在镜像下载过程中进一步裁决：本地不做 MySQL 验收，所有验收改在远端 AMD64 MySQL 8.4 的随机隔离数据库中执行。下载已立即中止，本地镜像不再属于验收路径。

## 12. 最终验收结果

2026-09-15 完成验收：

- 部署预检直接读取本地 `config.yaml`，只执行连接、Ping、版本和编译架构查询，确认目标为 MySQL 8.4.5、x86_64。
- 11 个集成测试文件的 17 组真实数据库场景全部改用 128 位随机 `trading_test_` 隔离数据库；MySQL 主包与 `dbtest` 子包全部通过，DROP 清理失败会使测试失败。
- 新增回归测试证明配置中的业务库名会被替换且原配置不被修改；CREATE 返回不确定错误时，已注册的 Cleanup 仍按顺序执行 `DROP DATABASE IF EXISTS` 和连接关闭。
- Testcontainers 与 MySQL 5.7/8.0 依赖、测试矩阵及现行文档承诺已经删除；八份旧计划/规格明确标记为废止，不再提供可误执行的旧版本指令。
- 前端语句覆盖率 93.06%，Go 总覆盖率 85.6%；market 94.3%、indicator 91.3%、strategy 94.8%、backtest 90.4%。Race Detector、静态检查、文档契约和全市场性能门禁通过。
- 应用镜像以 `linux/amd64` 成功构建，并确认最终镜像没有代理环境变量。完整脚本的后续单次重跑在最后的容器内 npm 下载遇到代理 `ECONNRESET`；此前相同最终 Dockerfile 的代理化 AMD64 构建已成功。用户知悉后明确裁决直接合并，因此该网络波动不阻塞本次归档。

## 13. 代码—设计冲突与用户裁决

用户明确决定停止 MySQL 5.7/8.0 双版本支持，统一使用 MySQL 8。只读探测发现部署数据库实际为 MySQL 8.4.5 后，用户先批准 MySQL 8.4 LTS 跨架构方案，随后明确否决本地 MySQL 验收，裁决所有真实 MySQL 验收直接在远端服务的随机隔离数据库中运行。

独立审查发现环境变量 DSN、创建响应不确定清理和 8.4+ 表述仍有边界缺口。用户进一步裁决：以后 MySQL 测试直接读取本地 `config.yaml` 的数据库配置，并要求完成修订后合并回 `main`。实现同时采用审查方案 A：CREATE 前注册幂等清理、清除 Git 跟踪文件中的真实内网端点，并把支持范围收紧为已验证的 MySQL 8.4.x LTS。

最终复审发现旧计划/规格仍以命令式语言保留过期 MySQL 版本矩阵。用户再次选择方案 A：保留历史追溯价值，但统一标记为已废止，清理可执行旧指令并链接现行需求与设计。最终技术复审无阻塞发现；在完整脚本仅因容器内代理连接重置而失败后，用户明确要求直接合并。
