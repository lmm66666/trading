# 行情更新进度：需求

## 1. 问题与背景

当前 updater 提供手动全市场股票刷新接口，但仅返回 ACCEPTED，没有任务 ID 或进度查询。股票与期货调度器仅在结束时保存内存摘要。前端自选刷新只重新读取数据库报价，不触发采集。

用户的一轮更新通常持续 5 小时以上，需要在电脑工作台发起更新，了解运行状态、处理数量和失败情况，关闭电脑后任务继续，重新打开可以查看。

部署沿用一个 NAS updater、一个按需运行的电脑 workbench，以及 NAS 既有 MySQL；本地 mock 库独立。保持现有刷新周期、限频、证券范围与启动后等待首周期规则。现有股票范围上限 5000，期货为固定 8 个连续品种。首版按单用户、少量浏览器标签页设计，不增加账户、多副本或推送系统。

## 2. 已确认的产品边界

用户在本任务对两个问题明确选择：

- “记录中断，手动重新更新（推荐，首版更简单）”。
- “沿用现状：手动更新股票，展示股票与期货进度”。

随后用户提出避免任务断点与行情更新规则重复，助手核查代码后说明当前是增量窗口与发布去重，并未跳过当天已更新证券；提出“进度只观察记录、不增加任务断点和自动重试、跳过已更新证券另行讨论”，用户回复“ok”。该决定只确认上述范围，不代表批准本文件新增的接口和存储细节。

## 3. 需求与验收条件

| ID | 需求 | 可观察验收 |
|---|---|---|
| REQ-UP-001 | 全市场手动股票刷新获得可查询任务 ID | 快速受理、无需等采集结束；重复触发沿用 429 防重；不自动重发超时 POST |
| REQ-UP-002 | 定时股票、手动股票、定时期货统一展示运行进度 | 展示来源、状态、总数、成功/失败数、开始/结束时间、记录时间与最近进展 |
| REQ-UP-003 | 运行记录独立于行情更新决策 | 不读取任务成功/失败记录来筛选证券；不恢复队列游标；重跑仍按原范围与增量窗口执行 |
| REQ-UP-004 | 任务记录跨工作台关闭、刷新和 updater 重启保留 | 工作台重开恢复服务端记录；updater 重启将遗留非终态标为中断，不自动续跑 |
| REQ-UP-005 | 前端有独立数据更新入口 | 股票有手动按钮，期货仅展示；运行中禁止重复触发；关闭面板不取消任务 |
| REQ-UP-006 | 失败与失联不混淆 | 保留最后记录与时间，查询失败或心跳过期不把任务改成 FAILED；失败明细脱敏分页 |
| REQ-UP-007 | 不改动现有采集语义 | 保留当前 20 根日线重叠窗口、期货全历史刷新、共享限频、周期、防重、单证券同步刷新与版本发布逻辑 |
| REQ-UP-008 | 可观测性不成为采集正确性的前置条件 | 进度写入失败不回滚行情、不重复发布、不触发自动采集重试；中断计数明确为最后记录值 |

## 4. 范围与非目标

实现任务摘要、失败明细、查询接口、工作台入口与轮询。单证券同步刷新仍保持原接口，不纳入本次批量任务历史。

不实现：自动续跑、按任务断点重试、跳过当天更新证券、仅重试失败项、暂停/取消、期货手动触发、新采集周期、WebSocket、通用任务队列改造、多 updater 协作。

## 5. 兼容、审批与证据

现有空请求触发、单证券同步请求、HTTP 状态和错误语义保留；异步受理结果增加 run_id。新页面需要对应版本的 updater，升级按停止旧 updater、备份、启动新 updater、升级工作台进行，不设计长期新旧协议适配层。

本文件与 [设计](design.md) 已获准实施，批准范围和原始内容版本见元数据；本次仅覆盖进度观察与操作入口，不改变行情更新语义。验证进展见 [验证记录](verification.md)。

实际批准：用户在查看两张表及记录内容说明后回复“ok 没问题，执行吧”，批准上述版本需求与设计实施。此前待评审措辞保留为草案形成历史，以本批准记录为准。
