# 系统设计

| 属性 | 内容 |
|---|---|
| 状态 | 当前有效 |
| 最后更新 | 2026-09-19 |

## 1. 这个系统是什么

一个个人行情研究平台：从新浪采集 A 股与期货连续合约的日线和复权因子，保存为可追溯的数据版本；在其上计算指标、运行版本化策略，通过扫描得到候选名单、通过回测检验历史表现、通过图表浏览行情。全部结果绑定创建时的输入（行情版本、策略版本、参数、引擎版本），因此可以复查和解释，而不是只给一个答案。

`main.go` 是组合根：加载配置、连接 MySQL、装配适配器与调度器、启动 HTTP 服务和任务 Worker、优雅停机。它不承载业务规则。

```text
外部数据源 ──> Broker Adapter ──> Application ──> Port ──> MySQL
                                      │
HTTP / Web ──> API Adapter ───────────┤
                                      └──> Market / Indicator / Strategy / Backtest
```

## 2. 数据的一生：模块为什么这样分工

一条数据从进入系统到出现在你面前，经过四个阶段；每个阶段对应一组模块。

**采集**：`pkg/broker` 里的新浪适配器负责与外部来源对话——构造请求、限频、重试、把外部响应解析并校验成领域对象。外部 DTO 不越过这一层，后面的代码不需要知道新浪的格式。采集细节见 [行情采集与版本](../design/workflows/market-data.md)。

**存储**：`internal/infrastructure/mysql` 把观察写成带版本与修订的行，把任务、租约和结果原子持久化。它实现 `internal/port` 定义的接口；port 是应用层声明的"我需要什么存储能力"，让应用不直接依赖 GORM 和 SQL。

**计算**：三个纯领域模块不碰数据库和网络。`internal/market` 定义行情值对象、Bar、Dataset、复权换算和周线聚合；`internal/indicator` 在完整序列上计算带有效位的指标；`internal/strategy` 管理策略定义、注册、实例隔离和按时间回放。它们只依赖标准库和彼此，因此可以被确定性测试。

**编排与使用**：`internal/application` 把上面三者组合成用例——刷新一只证券、创建扫描或回测任务、查询图表；`api` 把 HTTP 请求翻译成应用调用再把结果映射回 JSON；`web` 是 React 工作台。`internal/backtest` 是独立的模拟引擎，消费策略决策并按执行假设撮合。

业务流程的完整阅读层在 `docs/design/workflows/`（采集、扫描、回测），具体策略规则在 `docs/design/strategies/`；本文不重复它们的内容，只在第 4 节给出索引。`data`、`model` 仅剩旧库迁移链路所需的连接初始化与兼容模型，不构成平行业务栈。

## 3. 全局业务不变量

以下规则跨模块生效，本节是它们的唯一权威位置；模块设计只说明自己如何满足。

### 3.1 时间与数值

- 瞬时时间使用 UTC `time.Time`，MySQL 使用 `DATETIME(6)`；进入持久化边界前截断到微秒。
- 交易日期使用独立 date-only 语义，不用自由格式字符串或带时区时间戳替代。
- Price 和 Money 使用缩放 10000 的有符号整数；版本与序号使用无符号整数。

### 3.2 身份

- 证券使用包含交易所的完整身份，例如 `SSE:600000` 或 `SHFE:AU.MAIN`。
- 不透明身份字段按 UTF-8 字节限制，精确区分大小写和尾空格。
- API、领域校验和数据库列必须实施一致的长度与比较语义，不能由数据库截断或大小写不敏感排序规则修正输入。

### 3.3 行情版本

- 新计算只读取大于 0 的 `COMPLETE` 行情版本。
- 请求使用版本 0 时只允许在入口解析一次最新完成版本；任务执行和后续分页始终绑定解析后的正版本。
- 行情发布先形成不可见的新版本，全部校验与写入完成后一次切换为 `COMPLETE`；消费者不得看到部分版本。
- 发布是增量观察：缺失键不代表删除；内容与上次相同（摘要一致）不产生新版本。
- 周线由日线本地确定性聚合，只发布已经结束的 ISO 周；当前周进入下一 ISO 周后才成为可发布周线。

### 3.4 策略与回测时间线

- 指标预热期返回无效值，不用零值伪装有效结果。
- 信号在当前 Bar 收盘后产生，订单最早在下一根可交易 Bar 开盘成交。
- 策略不得读取未来 Bar；修复旧的未来数据问题可以改变历史信号与收益。
- 策略行为变化必须新增策略版本；撮合、成本或引擎语义变化必须提升 `EngineVersion`。

### 3.5 任务和结果

- 回测和扫描任务固定行情版本、证券集合、策略版本、参数、执行配置与引擎版本，从而能够重复执行。
- HTTP 请求结束或同步等待超时不取消已经持久化的任务；显式取消和服务停机有独立语义。
- 扫描一次最多处理 5000 个证券，必须通过 `BatchDatasets` 有界批量加载，不恢复逐证券 Repository 查询。
- 单证券失败允许扫描得到 `PARTIAL_SUCCEEDED`；成功结果与失败分类在同一不可变快照发布。
- 快照分页绑定 `SnapshotID` 和持久化序号，新快照发布不得改变已经开始的分页。

## 4. 端到端流程索引

每条链路的完整说明（窗口、规则、例子、失败场景）在业务流程文档；本节只保留方向。

### 4.1 行情采集与发布

调度器或手动刷新触发应用服务 → Broker 在共享限频器下请求新浪 → 应用服务验证并在本地聚合周线 → MySQL 适配器在短事务内分配版本、写入修订并原子切换 `COMPLETE` → 读取方只解析完成版本。完整链路：[行情采集与版本](../design/workflows/market-data.md)。

### 4.2 图表与行情查询

API 校验证券、周期、价格视图、范围、版本和指标预算 → 应用服务解析一次完成版本，在完整历史上下文计算指标 → 返回页按时间升序，向前分页继续使用相同版本和排他游标 → 客户端取消陈旧请求，不能让旧响应覆盖新查询状态。HTTP 契约见 [API 文档](../standards/http-api.md)。

### 4.3 扫描

创建请求固定策略定义、参数、时间窗、证券集合和行情版本 → 持久化 Worker 领取带租约的任务并定期续租 → 应用层批量读取全市场数据，为每只证券创建独立策略实例 → 结果稳定排序后，与失败分类、Run 终态和完成事件原子发布 → 后续读取通过 SnapshotID 保持不可变分页。完整链路：[策略扫描流程](../design/workflows/strategy-scan.md)。

### 4.4 回测

创建请求固定证券、策略、行情版本和完整执行配置 → Worker 加载带预热上下文的数据，账户从请求窗口开始 → 策略按时间线产生动作，撮合器在下一可交易 Bar 执行订单并计算费用 → 汇总、订单、成交、权益、Run 终态和完成事件原子发布 → 取消、失租或引擎失败不得发布成功结果。完整链路：[回测流程](../design/workflows/backtesting.md)。

## 5. 一致性与失败边界

- 外部 HTTP 不在数据库事务中执行，长计算不持有数据库事务。
- 数据库唯一约束、条件更新和稳定锁顺序负责并发仲裁，应用层预检查不能替代数据库约束。
- 可重试只适用于明确的临时、超时、死锁或连接类错误；取消、失租和确定性业务错误不重试。
- 错误沿调用链用 `%w` 保留原因，只在有处理责任的边界记录一次；API 和持久化结果不得泄露 SQL、凭据、路径、响应正文或堆栈。
- 批量任务汇总成功与失败数量，不在高频循环逐 Bar 或逐 SQL 输出 Info 日志。
- 进程内刷新守卫与租约只对本进程有效；本系统按单实例部署设计，不引入跨进程协调。

## 6. 部署与迁移

- Go 1.25.7+、Node.js 24+、MySQL 8.4.x LTS。
- 镜像不包含本地配置、凭据、转储或导出包，进程以非 root 用户运行，配置只读挂载。
- 本项目允许停机更新。数据库语义变化默认按“停服务、备份、迁移、校验、启动”执行。
- 不默认建设双写、影子表、灰度读、在线回填或长期跨版本兼容；只有明确不停机需求或数据量证明确需在线迁移时才增加复杂度。

## 7. 质量门禁

测试顺序、覆盖率阈值、快速检查、完整门禁及 Docker 不可用时的报告要求统一以 [工程标准](../standards/engineering.md) 的“测试与交付”章节为准。本设计只定义系统边界，不复制工程门禁数值。
