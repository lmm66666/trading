# Go 策略与回测内核整体迁移设计

## 1. 背景

当前系统已经具备日线、周线、财报采集，以及 `daily_b1_buy`、`weekly_b1_buy`、`bottom_surge_pullback` 三个技术策略，但策略能力仍建立在 `filter` 数组和批量布尔结果之上，所谓回测也只返回历史信号日期，没有订单、成交、持仓、资金曲线和交易成本。

全市场扫描目前先查询约 5000 个股票代码，再为每只股票执行一条最近 K 线 SQL。虽然通过 goroutine 并发执行，但查询数量仍与股票数量线性增长，数据库连接池和往返延迟成为主要瓶颈；单只查询错误还会被静默忽略。扫描结果不持久化，因此相同数据和相同策略会被重复加载、重复计算。

项目后续希望逐步发展为类似 TradingView 的分析平台，支持指标、策略脚本和回测。第一阶段只建设后端内核，不建设图表编辑器或通用脚本语言；策略直接使用 Go 编写。

## 2. 目标

1. 建立无未来函数、可复现、可扩展的指标、Go 策略和单标的回测内核。
2. 一次性迁移三个现有技术策略，删除旧 `pkg/filter`、`pkg/strategy` 技术策略执行链，不长期维护双引擎。
3. 将全市场扫描由逐股 SQL 改为按周期批量加载、内存分组计算和持久化信号快照。
4. 将回测从“信号日期列表”升级为包含订单撮合、交易成本、持仓、成交、权益曲线和绩效指标的真实流程。
5. 引入原始价格、复权因子和公司行动双价格视图，避免除权除息制造虚假信号或错误收益。
6. 使用持久化任务模型承载扫描和回测，并为以后替换 Redis、Kafka 保留清晰端口。
7. 保持现有 HTTP 路径可用，但内部统一路由到新 application service。

## 3. 非目标

- 第一阶段不提供 Pine Script 或自定义 DSL。
- 不允许运行用户上传的 Go 源码、插件或动态二进制；Go 策略必须随服务编译并登记。
- 不建设前端图表、策略编辑器或可视化调参界面。
- 不支持组合级回测、多股票共享资金、做空、融资融券、期货保证金、加仓或金字塔持仓。
- 不引入 Redis、Kafka、微服务拆分或分布式计算集群。
- 财报筛选不迁入 K 线回测引擎；其现有规则原样迁到独立 `internal/financialscreen`，以便删除旧 `pkg/filter`、`pkg/strategy` 目录，同时保持财报 API 行为不变。
- 不保证与旧引擎中存在未来数据访问或不完整均线预热的错误结果一致。

## 4. 核心架构决策

### 4.1 采用混合执行模型

指标和派生特征采用向量化预计算，策略决策和订单撮合采用逐 Bar 推进：

1. `FeatureGraph` 根据策略声明的依赖，一次性计算 SMA、EMA、MACD、KDJ、成交量均线等序列。
2. 回测引擎按时间顺序推进，每个时间点只向策略暴露当前及过去已确认数据。
3. 策略返回 `Hold`、`EnterLong` 或 `ExitLong` 意图，不直接修改账户和订单。
4. 引擎在下一根 Bar 的开盘阶段撮合上一根 Bar 收盘后产生的意图。

该模型兼顾指标计算效率和真实交易时序，同时为未来 DSL 预留稳定的 Strategy 接口。

### 4.2 领域内核保持纯净

`internal/market`、`internal/indicator`、`internal/strategy` 和 `internal/backtest` 不依赖 Gin、GORM、MySQL 或网络客户端。所有输入通过明确的领域值对象传入，核心计算必须是确定性的，并可在单元测试中完全运行。

### 4.3 一次性切换执行链

迁移完成后：

- 三个技术策略全部由新 Strategy Registry 创建。
- 扫描和回测全部调用同一个策略接口与 FeatureGraph。
- 删除旧技术 `filter` 组合和旧 `pkg/strategy` 实现。
- 现有 HTTP 路径只作为传输层兼容适配器，不保留旧业务实现。

数据迁移采用“新表建好、校验通过、运行时一次切换”的方式。旧行情表在切换后只保留为只读回滚备份，不被运行时读取；确认稳定并完成数据库备份后再由独立运维变更删除，避免不可恢复的数据破坏。

## 5. 目标模块

```text
internal/
  market/                 Bar、Timeframe、Instrument、Dataset、公司行动、多周期对齐
  indicator/              Series、SMA、EMA、MACD、KDJ、VMA、FeatureGraph
  strategy/               Strategy、Context、Action、Registry、ExitPolicy
    builtin/              三个内置 Go 策略
  financialscreen/        财报筛选规则，不参与 K 线回测

  application/            RunBacktest、ScanSignals、任务编排、输入输出 DTO
  port/                   MarketData、RunStore、JobQueue、EventBus、SignalCache
```

依赖只能由外向内：API 和 infrastructure 依赖 application 与 domain，domain 不反向依赖外层。`main.go` 只负责配置加载、依赖装配和生命周期管理。

## 6. 领域模型与接口契约

### 6.1 市场数据

`Instrument` 使用“市场 + 代码”作为业务唯一标识，例如 `SSE:600000`、`SZSE:000001`，避免仅使用六位代码产生证券类型或市场冲突。外部 API 暂时仍可接收六位代码，但必须在边界解析为唯一 Instrument。

`Bar` 至少包含：

- Instrument
- Timeframe
- OpenTime、CloseTime
- 原始 Open、High、Low、Close、Volume、Amount
- TradingStatus、LimitUp、LimitDown
- 数据源、数据版本

`Dataset` 在创建时完成排序、去重、OHLC 合法性和时间连续性校验。领域层不接受未校验的 GORM Model 指针。

### 6.2 指标与特征图

指标输出使用带有效位的 Series。SMA(20) 在不足 20 根有效 Bar 时返回 invalid，不再用 1 至 19 根数据计算“部分均线”。

每个 Feature 必须满足前缀一致性：

```text
Compute(all)[:k] == Compute(all[:k])
```

同一个 Dataset 内，相同参数的 Feature 只计算一次。Feature key 由指标名称、参数、价格视图和周期共同组成，避免不同策略重复计算。

### 6.3 策略契约

每个策略声明：

- 稳定 ID 和版本。
- 主周期和最小预热 Bar 数量。
- 参数定义、默认值和校验规则。
- 所需 Feature 列表和辅助周期。
- 默认退出策略。

`StrategyContext` 只允许访问：

- 当前 Bar 和当前索引。
- `Float(feature, ago)`、`Bool(feature, ago)`。
- 当前只读持仓视图。
- 当前已确认的辅助周期特征。

`ago=0` 表示当前已收盘 Bar，`ago>0` 表示历史；负数立即返回领域错误。策略无法获得未来数组、Repository、数据库连接或可变账户对象。

### 6.4 注册表

Strategy Registry 使用策略 ID、版本和参数创建策略实例。数据库只保存这些元数据，不保存代码。未知策略、未知参数、越界参数或版本不兼容必须在任务入队前返回明确错误。

## 7. 双价格视图与公司行动

### 7.1 使用口径

- 指标和策略判断使用前复权价格视图，避免除权缺口制造虚假技术信号。
- 订单撮合、现金、持仓成本和权益核算使用原始价格。
- 除息日开盘前将现金分红计入账户；送股、转增、拆并股调整持仓数量和单位成本。
- 配股等无法完整建模的公司行动必须显式标记；在缺少必要参数时，回测 fail-fast，不生成不可信结果。

### 7.2 数据版本

行情及公司行动采用可追溯版本。每次成功采集形成一个 dataset version；修订已有 Bar 时保留历史修订，而不是覆盖后无法还原。版本记录使用 `valid_from_version` 和 `valid_to_version` 表示可见区间，读取版本 V 时只选择 `valid_from_version <= V` 且 `valid_to_version` 为空或大于 V 的记录。回测和扫描记录引用确切的数据版本，保证相同策略版本、参数、引擎版本和数据版本能够重放出相同结果。

迁移时从现有日线、周线表生成首个版本。若历史数据缺少复权或公司行动资料，则先标记数据集为 `INCOMPLETE`；需要真实收益的回测拒绝使用不完整数据，信号扫描可在响应中明确标记数据质量，不得静默降级。

## 8. 多周期语义

`weekly_b1_buy` 的主时钟为周线。周线策略在某周 CloseTime 做判断，只能读取 `daily.CloseTime <= weekly.CloseTime` 的最后一个已确认日线特征，禁止通过字符串日期精确相等或读取后续交易日。

周线收盘产生的交易意图在下一根周线 Bar 的 Open 成交，即下一交易周首个可交易开盘。辅助周期只提供特征，不改变主时钟推进速度。

第一阶段仅实现日线主时钟和周线主时钟，以及周线读取日线 MA20 的最小跨周期能力，不建设任意周期聚合图。

## 9. 回测语义

### 9.1 范围

- 单股票、单策略。
- 仅做多。
- 同一时间最多一个仓位。
- 默认使用 100% 可用现金，按配置的现金比例和证券最小交易单位向下取整。
- 初始资金、佣金、最低佣金、印花税、过户费、滑点和仓位比例全部通过已校验配置传入。

### 9.2 每根 Bar 的处理顺序

1. 在当前 Bar 开盘前应用当日公司行动。
2. 尝试撮合上一根 Bar 收盘后生成的订单。
3. 更新现金、持仓、成本和成交记录。
4. 使用当前 Bar 收盘价计算权益。
5. 策略读取当前及历史已确认信息并返回 Action。
6. 引擎把 Action 转换为下一根 Bar 有效的订单。

最后一根 Bar 产生的 Action 没有下一根开盘价，因此保持未成交并记录原因。期末未平仓仓位按最后收盘价估值，不伪造平仓交易；胜率只统计已平仓交易。

### 9.3 成交约束

- `volume=0` 或 TradingStatus 不可交易时不成交。
- 买入开盘价达到涨停价、卖出开盘价达到跌停价时不成交。
- 下一开盘订单有效期为一个 Bar；未成交的入场订单取消，不在后续日期偷偷成交。
- 退出条件在持仓期间持续成立时，策略在后续收盘继续发出退出意图，因此遇到停牌或跌停后会在下一可尝试时点重新下单。
- 滑点作用于开盘价，最终成交价限制在该 Bar 的 High/Low 范围内。
- 资金不足以购买一个最小交易单位时，订单拒绝并记录结构化原因。

### 9.4 默认退出规则

默认 `hold_bars=10`，可由策略参数覆盖。买入成交所在 Bar 计为持有第 1 根；第 10 根持有 Bar 收盘后产生退出意图，在下一根 Bar 开盘卖出。第一阶段不提供默认止盈、止损和移动止损，未来具体 Go 策略可替换 ExitPolicy。

### 9.5 输出

回测结果至少包含：

- 总收益率、年化收益率、最大回撤。
- 已平仓交易数、胜率、盈亏比、平均持有 Bar 数。
- 订单和未成交原因。
- 每笔成交及费用。
- 每日或每周权益曲线、现金、持仓市值和回撤。
- 期末未平仓状态。

## 10. 三个策略迁移

### 10.1 `daily_b1_buy`

保留现有业务参数：倍量阈值 2.0、相对前收涨幅至少 5%、最大回调 15%、最长回调 10 根，KDJ 低位阈值 40，MA20 趋势观察 10 根。所有窗口改为向前状态机，任何日期的结果只能依赖该日期及之前的数据。

### 10.2 `weekly_b1_buy`

保留四个条件：周线 KDJ 小于 10、周线 MA20 位于 MA60 之上、周收盘站上周 MA60、周收盘站上截至该周收盘已确认的日 MA20。均线未完成预热时不产生信号。

### 10.3 `bottom_surge_pullback`

保留现有主要参数：60 日低位上浮不超过 15%、单日量比至少 2 且涨幅至少 5%，或连续 3 日量比至少 1.2 且涨幅至少 2%；允许 3 日放量间隔；最大回调 20%、最长 15 根；MA20 在 MA60 上方、价格站上 MA60、KDJ J 值在 -20 至 20。

当前实现会先在完整数组中寻找后续峰值，再回填过去日期的有效结果，存在未来数据污染。新实现使用正向状态机维护 `Idle → Surge → Rally → Pullback → Complete/Invalid`，只在状态随当前 Bar 演进时输出信号。修复后的历史信号允许与旧结果不同。

## 11. 数据存储设计

### 11.1 核心表

| 表 | 用途 | 关键约束 |
|---|---|---|
| `t_instruments` | 证券主数据和扫描范围 | `(exchange, code)` 唯一 |
| `t_market_data_versions` | 一次成功采集的数据版本 | version 唯一，状态不可回退 |
| `t_market_bars` | 统一日线、周线及未来周期的原始 Bar 修订 | `(instrument_id, timeframe, close_time, revision)` 唯一 |
| `t_adjustment_factors` | 前复权因子版本 | `(instrument_id, effective_time, data_version)` 唯一 |
| `t_corporate_actions` | 分红、送转、拆并股、配股事件 | 事件来源标识唯一 |
| `t_compute_runs` | 回测和扫描任务、租约及幂等键 | `(kind, idempotency_key)` 唯一 |
| `t_backtest_runs` | 回测输入、版本和汇总指标 | `run_id` 唯一 |
| `t_backtest_orders` | 订单及拒绝原因 | `(run_id, sequence)` 唯一 |
| `t_backtest_trades` | 成交和费用 | `(run_id, sequence)` 唯一 |
| `t_backtest_equity_points` | 权益曲线 | `(run_id, sequence)` 唯一 |
| `t_signal_snapshots` | 某策略、数据版本和时点的不可变快照 | 业务组合唯一 |
| `t_signal_snapshot_rows` | 快照命中的股票及信号上下文 | `(snapshot_id, instrument_id)` 唯一 |
| `t_outbox_events` | 本地可靠事件及未来 Kafka 转发源 | 事件 ID 唯一 |

`t_market_bars` 的版本查询由 Repository 封装，application 和 domain 不接触修订 SQL。原始 Price 和 Money 在领域中使用缩放 `int64` 值对象，默认精度为万分之一元；指标 Series 可使用 `float64` 做数学运算，但订单、费用、现金和权益必须按明确规则转换和舍入，禁止用二进制浮点直接累加资金。

现有 `model/README.md` 要求所有日期以字符串保存，这与多周期 CloseTime、时区和精确排序冲突。本次迁移同步更新该规范：持久化时间统一使用 UTC `time.Time`，传输层按 RFC 3339 输出；纯交易日期另用 `TradingDate` 表示。所有新表仍显式定义表名和审计字段。

### 11.2 索引与批量加载

- 股票范围从 `t_instruments` 读取，不再对千万级 K 线执行 `DISTINCT code`。
- Bar 使用 `(timeframe, close_time, instrument_id)` 范围索引和 `(instrument_id, timeframe, close_time)` 单标的索引。
- 为兼容 MySQL 5.7，不依赖窗口函数。全市场扫描按交易日期范围用每个周期固定数量的 SQL 批量取回，再在 Go 中按 Instrument 分组并截取所需 Bar。
- 批量写入订单、权益点和快照行，不逐条提交事务。
- FeatureGraph 在同一次扫描中跨策略复用相同特征。

这样数据库查询次数由“股票数量级”降为“周期和批次数量级”。

## 12. 扫描与性能模型

### 12.1 执行流程

1. 创建 Scan Run，锁定策略版本、参数、数据版本和 as-of 时间。
2. 从证券主数据加载扫描范围。
3. 按周期批量加载所需日期窗口的 Bar、复权因子及辅助周期数据。
4. 在 Go 中校验并构造每个 Instrument 的 Dataset。
5. 使用固定大小 worker pool 计算 FeatureGraph 和最新 Action，不为每只股票无界创建 goroutine。
6. 将成功信号和逐股失败原因批量写入临时快照版本。
7. 同一事务中发布完整快照并更新任务状态。
8. 查询接口直接读取最新成功快照。

### 12.2 增量更新

行情版本发布后，将受影响的 Instrument 标记为 dirty。下一次扫描只重算 dirty Instrument，并与上一不可变快照合并生成新快照。策略版本、策略参数、复权因子或公司行动变化时，相应快照整体失效。

### 12.3 性能目标

在固定 5000 股票测试集和约定基准环境中：

- 热数据全市场扫描不超过 8 秒，并相对迁移前约 40 秒至少提升 5 倍。
- 已生成信号快照查询 P95 不超过 200ms。
- 扫描 SQL 数量不随股票数量线性增长。
- 输出数据加载、分组校验、指标计算、策略判断和结果写入的分段耗时。

## 13. 任务、Redis 与 Kafka 边界

### 13.1 首期实现

扫描和回测统一使用 MySQL 持久化任务。worker 通过带过期时间的租约领取任务并定期续约；进程崩溃后其他 worker 可以接管。首期不增加 Redis 或 Kafka 运维依赖。

任务状态为：

```text
PENDING → RUNNING → SUCCEEDED
                  ↘ PARTIAL_SUCCEEDED
                  ↘ FAILED
PENDING/RUNNING → CANCELLED
```

### 13.2 可替换端口

- `JobQueue`：首期 MySQL，未来可替换 Redis Stream。
- `SignalCache`：首期读取 MySQL 快照，热点查询出现后可增加 Redis。
- `EventBus`：首期使用进程内通知加数据库 outbox 语义，进入分钟线、Tick 和多消费者阶段后可替换 Kafka。

只有在多实例协调、热点状态读取确实压垮 MySQL 时引入 Redis；只有在实时行情需要被指标、策略、通知、落库等多个消费者顺序消费和回放时引入 Kafka。替换 adapter 不改变 application 和 domain 接口。

```text
GET  /api/v1/backtest-runs/:run_id/equity

POST /api/v1/scan-runs
GET  /api/v1/scan-runs/:run_id
POST /api/v1/scan-runs/:run_id/cancel
GET  /api/v1/signal-snapshots/latest?strategy=...
```

创建接口接收幂等键并返回 `202 Accepted` 与 `run_id`。分页结果使用稳定 sequence 游标，避免大权益曲线一次性返回。

### 14.2 现有路径

- `GET /api/stocks/signal?strategy=` 改为读取最新成功快照，保持 `{name, codes}` 数据形状；没有快照时返回明确的 `SIGNAL_SNAPSHOT_NOT_READY`，不在查询请求中触发全市场计算。
- `GET /api/stocks/backtest` 作为同步兼容适配器：内部创建持久化 Run 并等待单股任务；在请求时限内完成则返回完整结果，超时则返回 `202` 和可继续查询的 `run_id`。
- 所有现有路径和 `api/api.md` 同步更新，删除已经下线的评分字段说明。

## 15. 错误处理与恢复

- 数据库超时、行情源短暂失败等可恢复错误最多自动重试 3 次并退避。
- 参数错误、策略不存在、版本不兼容、数据不完整和确定性策略错误直接失败。
- 单股回测 fail-fast；全市场扫描允许部分成功，但必须保存失败股票、错误分类和数量。
- 相同 kind 和幂等键重复提交返回已有 Run。
- worker 在批次和 Bar 边界检查取消状态。
- 任务结果完整写入后才切换为成功；快照通过事务发布，查询者看不到半成品。
- API 返回稳定业务错误码，内部 SQL、路径、堆栈和凭据只进入受控日志，不返回客户端。

## 16. 可观测性

结构化日志统一携带 `run_id`、策略 ID/版本、Instrument、Timeframe、数据版本。指标至少包括：

- 排队时间、租约接管和重试次数。
- 数据加载耗时、返回行数和 SQL 批次数。
- Dataset 校验、FeatureGraph、策略执行和持久化耗时。
- 成功、跳过和失败股票数量及错误分类。
- 快照查询延迟和命中版本。

不得在日志中记录数据库密码、完整配置文件、授权头或未经限制的请求体。

## 17. 安全设计

- 只执行编译进服务且登记在 Registry 的 Go 策略，不支持上传或动态编译任意代码。
- 参数使用白名单结构解析并设置范围、日期跨度、股票数量和分页上限。
- worker 并发度、数据库批次、内存预算和任务超时均通过配置限制。
- Docker 镜像不得复制 `config-nas.yaml` 或任何真实凭据；配置在运行时通过挂载文件或环境安全注入。
- 当前 Dockerfile 会复制 `config-nas.yaml`，且 `.dockerignore` 没有忽略该文件和导出镜像。迁移必须修复构建规则；凡是曾用于构建镜像的真实数据库凭据都要在部署前轮换，并废弃含凭据的旧镜像或导出包。
- 迁移程序在删除或归档旧表前必须完成备份、计数和校验，不自动执行不可恢复删除。

## 18. 测试策略

### 18.1 单元与性质测试

- domain、indicator、strategy 和 backtest 核心覆盖率不低于 90%，全项目覆盖率不低于 80%。
- 指标覆盖固定样例、空值、非法周期、预热边界和前缀一致性性质。
- 回测覆盖下一开盘成交、费用、滑点、最小交易单位、10 Bar 退出边界、最后 Bar、期末未平仓、停牌、涨跌停和公司行动。
- 三个策略使用表驱动场景和固定数据集 golden test；有意修复的旧错误以行为变更测试记录。
- 同一输入重复运行的订单、成交、权益和指标必须逐项一致。

### 18.2 集成与契约测试

- Repository、版本查询、任务租约、接管和快照事务使用真实 MySQL 5.7 与 8.0 集成测试，不使用 SQLite 替代数据库语义。
- API contract test 覆盖参数校验、幂等提交、状态转换、取消、分页、部分成功和脱敏错误。
- 数据迁移测试比较旧表和新表的 Instrument 数、Bar 数、日期范围、抽样 OHLCV 与校验摘要。
- 执行 `go test -race ./...` 检查 FeatureGraph 缓存和 worker 并行安全。

### 18.3 性能测试

固定生成或脱敏保存 5000 股票基准数据集，基准必须在变更前后使用相同环境、数据量、策略和数据版本。CI 记录趋势，正式验收环境执行 8 秒、5 倍和 P95 目标。

## 19. 迁移顺序与发布策略

虽然运行时一次性切换，工程实现仍按可验证依赖顺序提交：

1. 新领域值对象、指标 Series、FeatureGraph 及测试。
2. 新 Strategy 契约、Registry 和三个正向 Go 策略及测试；财报筛选迁到独立模块并保持行为不变。
3. 回测订单、撮合、账户、退出策略、指标及测试。
4. 统一行情、复权、公司行动和版本表，以及旧数据迁移器。
5. MySQL 批量查询、任务租约、Run/快照存储和性能基准。
6. application use case、新 API 和现有路径适配器。
7. 切换依赖装配，删除旧技术策略执行链，更新文档。
8. 全量测试、竞态、覆盖率、安全检查、迁移演练和性能验收。

发布前必须在数据库备份副本上完成全量迁移演练。正式发布采用维护窗口：暂停采集和扫描，迁移并校验数据，部署新应用，生成首批快照，验证后恢复入口。任何校验失败都停止切换并继续使用旧应用与旧表。

## 20. 验收标准

1. 三个技术策略只能通过新 Registry 和新执行内核运行，旧技术 filter/strategy 执行代码已删除。
2. 任意历史时点的策略输入不包含未来 Bar；全部指标通过前缀一致性测试。
3. 单股回测产生真实订单、成交、费用、持仓、权益曲线和约定绩效指标。
4. 回测结果记录策略、引擎、参数和精确数据版本，可确定性重放。
5. 扫描不再执行逐股 SQL，错误不被静默吞掉，并生成不可变快照。
6. 现有信号与回测 HTTP 路径继续可用，API 文档与真实响应一致。
7. 固定数据集达到全市场扫描不超过 8 秒、至少 5 倍提升、快照查询 P95 不超过 200ms。
8. 全部测试、`go vet`、竞态检查通过，核心覆盖率不低于 90%，全项目覆盖率不低于 80%。
9. 镜像和构建上下文不包含真实配置或凭据，已暴露风险完成凭据轮换。

## 21. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| 复权及公司行动数据源不完整 | 数据质量状态、版本校验、回测 fail-fast，不静默近似 |
| 修复未来函数导致信号变化 | golden test 固化新语义，并在发布说明中明确 breaking behavior |
| 全量迁移时间过长 | 备份副本演练、批量写入、迁移进度和维护窗口 |
| 权益点导致存储增长 | 批量写入、按 Run 索引、保留策略配置；不牺牲首期图表所需数据 |
| MySQL 任务竞争 | 租约、条件更新、幂等键、崩溃接管和真实 MySQL 并发测试 |
| 新抽象过度复杂 | 只实现日/周线、三策略、单仓做多和必要端口，不提前实现 DSL 或分布式中间件 |
| 旧接口同步等待超时 | 超时返回持久化 `run_id`，客户端可无损转异步查询 |
